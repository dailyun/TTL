# TodoTodoList PRD v0.1

## 1. 版本目标

v0.1 的目标是做出一个单用户可用的想法、Todo 与事件管理 Web 应用。它需要支持快速记录、版块分类、状态推进、本地日历视图、GitHub 私有库远端数据存储和 Google Calendar 双向同步的基础能力。

本版本不追求复杂协作。同步能力从第一阶段就按双向同步建模，但可以通过清晰的范围控制降低风险：先支持单用户、单 GitHub 私库、单 Google Calendar 的稳定同步。

## 2. 默认产品假设

这些是假设，不是最终决策：

- 用户主要是个人使用。
- 第一屏已确定采用「收集箱 + 今日 + 正在」组合，而不是纯看板或纯日历。
- 核心对象分为 Todo、Idea、Event。
- 状态包含：想要、正在、搁置、放弃、完成。
- GitHub 私有库是用户可自由读取的远端数据仓库。
- IndexedDB 是本地缓存、离线写入和同步队列。
- Google Calendar 第一版直接做双向同步。

## 3. 目标用户故事

### 快速记录

作为用户，我希望能在几秒内记录一个想法、Todo 或事件，避免想法在分类前流失。

验收标准：

- 可以从任意主视图打开快速新增。
- 只填标题即可创建。
- 默认类型为 Idea，默认状态为想要。
- 可以在新增时选择类型、版块、状态、时间。

### 管理 Todo

作为用户，我希望能看到自己当前正在推进的事项，并把任务从想要推进到正在、完成或搁置。

验收标准：

- 可以创建、编辑、删除 Todo。
- 可以修改 Todo 状态。
- 可以按状态过滤 Todo。
- 可以为 Todo 设置日期或时间段。
- 有时间的 Todo 会显示在日历视图中。

### 管理想法

作为用户，我希望把还不确定要不要执行的内容作为想法保存，不强迫它马上变成任务。

验收标准：

- 可以创建 Idea。
- Idea 可以长期停留在想要状态。
- Idea 可以转成 Todo。
- Idea 可以被标记为搁置或放弃。

### 管理事件

作为用户，我希望管理已经确定时间的事件，例如会议、约会、行程。

验收标准：

- Event 必须有开始时间。
- Event 可以有结束时间或全天属性。
- Event 默认显示在日历视图。
- Event 可归属工作、生活或自定义版块。

### 版块分类

作为用户，我希望把内容按工作、生活等版块组织，减少不同领域之间的干扰。

验收标准：

- 系统默认创建工作、生活两个版块。
- 用户可以创建、重命名、归档自定义版块。
- 每条 Item 必须归属一个版块，未选择时进入收集箱。
- 可以按版块筛选列表、看板和日历。

### 状态看板

作为用户，我希望用看板方式看到事项在不同状态中的分布。

验收标准：

- 看板包含想要、正在、搁置、放弃、完成五列。
- Item 可以通过拖拽或菜单修改状态。
- 默认视图可以隐藏放弃和完成，也可以手动显示。
- 每列显示数量。

### 日历视图

作为用户，我希望把有时间的事项放进日历里看，避免任务列表和真实日程脱节。

验收标准：

- 支持月视图、周视图、日视图中的至少一种，MVP 推荐先做周视图。
- 有 startAt 的 Todo 和 Event 显示在日历上。
- 可以从日历新建 Event。
- 可以点击日历项打开详情。

### 数据导入导出

作为用户，我希望自己的数据可导出、可恢复，避免被产品锁死。

验收标准：

- 可以导出 JSON 文件。
- 可以从 JSON 文件恢复。
- 导入前提示覆盖、合并或取消。
- 导出数据包含 items、sections、settings 和 sync metadata。

### GitHub 私有库数据源

作为用户，我希望我的数据保存在自己控制的 GitHub 私有库中，这样我可以从其他工具、脚本或设备自由读取和备份数据。

验收标准：

- 可以配置 GitHub owner、repo、branch 和数据路径。
- 应用可以从 GitHub 私有库初始化本地数据。
- 应用可以把本地变更同步回 GitHub 私有库。
- GitHub 中的数据文件是稳定、可读的 JSON 文件。
- IndexedDB 数据可以从 GitHub 完整恢复。
- GitHub token 不暴露在前端代码或持久化浏览器存储中。

### GitHub 人工可读写文件源

作为用户，我希望能把 GitHub 私有库中已有的人工文件目录同步进系统，例如 `findwork/**/*.md`，这样我可以继续用编辑器或 GitHub 写 Markdown，同时让这些内容进入 TodoTodoList。

验收标准：

- 可以配置一个人工文件源，例如 `findwork/**/*.md`。
- Markdown 文件可以通过 YAML frontmatter 声明 type、status、section、tags、startAt、endAt。
- 没有 frontmatter 的 Markdown 可以按默认规则导入为 Idea。
- Markdown body 会进入 Item description。
- Markdown checkbox 可以导入为 Todo。
- 系统回写人工文件时默认只修改 frontmatter，不破坏正文。
- Item 详情能显示来源路径，例如 `findwork/product-plan.md`。

### Google Calendar 双向同步

作为用户，我希望本产品和 Google Calendar 能双向同步，避免同一个日程在两个地方重复维护。

验收标准：

- 可以授权并选择一个 Google Calendar。
- 本地 Event 可以创建或更新 Google Calendar 事件。
- Google Calendar 事件变化可以同步回本地 Event。
- 本地删除或放弃已同步 Event 时，有明确的删除或取消同步行为。
- 同一事件双边修改时，应用能识别冲突并提示用户处理。
- 重复事件第一版可以限制编辑范围，但不能静默错误覆盖。

## 4. MVP 功能列表

### P0 必须有

- Item 创建、编辑、删除。
- Todo / Idea / Event 三种类型。
- 工作 / 生活 / 收集箱。
- 状态：想要、正在、搁置、放弃、完成。
- 列表视图。
- 看板视图。
- 本地持久化。
- JSON 导入导出。
- GitHub 私有库初始化、拉取、推送。
- GitHub 人工 Markdown 文件源导入与 frontmatter 回写。
- Google Calendar 单日历双向同步。

### P1 应该有

- 日历周视图。
- 标签。
- 搜索。
- 自定义版块。
- 拖拽修改状态。
- 归档完成和放弃项。

### P2 可以后置

- 快捷键。
- 重复事项。
- 提醒通知。

## 5. 非目标

v0.1 暂不实现：

- 团队协作。
- 多用户权限。
- 评论和消息通知。
- 实时同步。
- 离线冲突自动合并。
- 原生移动端 App。
- AI 自动拆解任务。

## 6. 页面范围

MVP 页面：

- Home：收集箱、今日事项、正在事项。
- Items：全部事项列表。
- Board：状态看板。
- Calendar：本地日历。
- Sections：版块管理。
- Settings：数据导入导出，同步设置占位。

## 7. 核心指标

第一阶段更关注个人使用体验，不追求商业指标。

建议跟踪：

- 新增 Item 数量。
- 每周 active 状态 Item 数量。
- wanted 转 active 的数量。
- active 转 done 的数量。
- paused / abandoned 的清理数量。
- 日历事项占比。
- 用户是否持续导出或同步数据。

## 8. 权限与隐私

- 默认所有数据保存在用户本地。
- Google Calendar 连接需要清晰展示授权用途，尤其是读写日历权限。
- GitHub token 不应保存在前端明文中。
- 导出文件中应包含完整数据，但提示用户妥善保存。
- 如果后续做云端账号，需要重新设计数据权限和隐私政策。

## 9. 待确认

- 是否需要账号体系，还是先做纯本地个人工具。
- 自定义版块是否进入 MVP。
- 日历 MVP 是周视图优先还是月视图优先。
- 是否需要在 MVP 加入提醒。
- Google Calendar 双向同步第一版是否只支持单日历。
- GitHub 私有库同步第一版采用月分片还是单 snapshot。
- 人工文件源第一版是否只支持 Markdown。
